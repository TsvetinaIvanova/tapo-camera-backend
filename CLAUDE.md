# Tapo Camera Backend

Portfolio project for remote EU SRE/DevOps/Cloud roles. Everything should be defensible in an interview: least privilege, IaC for all AWS resources, CI/CD via OIDC, observable failure modes. Be direct and practical, flag tradeoffs honestly, and push back if something doesn't fit.

## What it does

A Raspberry Pi (hostname `rpi5`) polls Tapo cameras, downloads motion-triggered clips from their SD cards and uploads them to S3. An S3 PutObject event triggers a Lambda (ffmpeg thumbnail, then DynamoDB metadata). A query Lambda behind an API Gateway HTTP API serves clips (presigned URLs) to a static HTML frontend on S3.

Cameras (the names are used as `camera_id`, S3 prefixes and CloudWatch dimensions, so do not rename them):
- `c225_garage` 192.168.68.105 (wired, `timeCorrection=1`)
- `c325_back` 192.168.68.103 (wired)
- `c325_porch` 192.168.68.100 (wired)
- `c660_street` 192.168.68.109 (battery-powered, outdoor, slow Wi-Fi, partially captures a public road)

All cameras use the same Tapo camera account (`camera_admin`) and password. Third-party compatibility must stay enabled in the Tapo app.

## pytapo 3.4.14 rules (hard-won, do not deviate)

- `Tapo(ip, "camera_admin", PASSWORD, PASSWORD)`: the 4th arg (cloudPassword) must equal the password.
- Construct `Tapo()` outside any running event loop. In async code use `loop.run_in_executor` for `Tapo()`, `getRecordings` and `getTimeCorrection`.
- `getRecordings(date)` returns `[{'search_video_results_N': {'startTime','endTime','vedio_type'}}]`. `vedio_type` is always 2; per-clip person/vehicle type is not exposed.
- `Downloader(tapo, start, end, timeCorrection, outputDir + "/", None, False, None, fileName=...)`. The parameter is `overwriteFiles`. There is no "Done" action: success means `"Converting"` was seen and the generator exhausted.
- Failed logins burn a lockout counter on the camera (`max_time: 10`). Once exhausted it returns empty bodies or timeouts instead of clean errors. Never loop auth attempts while debugging.
- `Invalid authentication data` / `Incorrect device_confirm value` means a wrong password. `Expecting value: line 1 column 1` usually means lockout or a wrong device at that IP.
- `Error: STORAGE_NOT_EXIST` (-71114) on C660, occasional and non-consecutive, is expected and self-heals on the next poll. Investigate only if frequent or consecutive.

## Poller architecture (poller/poller.py)

- One thread per camera, each with its own long-lived event loop (not recreated per cycle; avoids "Task was destroyed but it is pending" from pytapo's async generators).
- Per-camera `interval_seconds` plus optional `night_mode` (slower interval, never zero, so there is no huge dawn backlog). C660's battery drain is driven by session length and wake count, so keep its backlog small.
- Startup is staggered (8s per camera). State file is lock-guarded and written after every uploaded clip (`persist_clip_progress`), so a restart resumes mid-cycle.
- Emits `PollCycleCompleted` and `PollCycleErrors` per camera via `put_metric_data`, and ships all logs to CloudWatch Logs via `watchtower`. Both are best-effort and must never block or crash uploads.
- Runs as systemd unit `tapo-poller` with `StateDirectory=tapo-poller` (state at `/var/lib/tapo-poller/state.json`). Verify the deployed paths and user with `systemctl cat tapo-poller`. Logs: `journalctl -u tapo-poller -f`.

## Conventions

- Terraform: every variable has a default (no prompts in CI), except `alert_email`: it is required on purpose so a missing value fails loudly instead of silently dropping alerting (CI: `TF_VAR_alert_email` secret; locally: `terraform.tfvars`). Plan runs on `pull_request` only. Least-privilege IAM per resource; the GitHub OIDC role is intentionally broad (service-level wildcards).
- CI: `actions/checkout@v6`, `actions/setup-python@v6`, `python -m pytest`. No stored AWS keys.
- Frontend never hardcodes the API endpoint (reads `config.json` at runtime). API auth is a shared secret sent as the `x-api-key` header, kept in localStorage.
- Lambda deploy: merging to `main` deploys; never `update-function-code` by hand. Query and authorizer are zips owned by Terraform (`archive_file` with `output_file_mode = "0644"` so zips are byte-identical locally and in CI). The processor is a container image: `deploy.yml` builds, smoke-tests and pushes it first, then `terraform apply` pins the function to that digest (`processor_image_digest`; PR/local plans fall back to the newest image).
- Never commit `config.yaml`, `config.json`, state files or `.tfstate`. Never print or log camera passwords or the API secret.
