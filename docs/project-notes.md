# Project notes: decisions, history, backlog

Imported by CLAUDE.md. Update this file when a decision is made or a backlog item changes state.

## Decisions (and why)

- **API auth: shared-secret Lambda authorizer.** `x-api-key` header checked against an SSM SecureString (generated by Terraform `random_password`), constant-time compare, 5-minute authorizer cache. Chosen over Cognito (free at this scale, but needs an OAuth/PKCE frontend rewrite plus CloudFront + ACM for HTTPS, and makes mobile access more awkward) and over a WAF IP allowlist (blocks access from other networks). Swapping to a Cognito JWT authorizer later only touches the API Gateway layer; the query Lambda is unaffected. CORS must allow the `x-api-key` header. Rotate with `terraform apply -replace=random_password.api_shared_secret`.
- **Frontend over HTTPS without CloudFront: use the bucket's regional REST endpoint.** The S3 website endpoint is HTTP only. `https://vladaya-tapo-cameras-frontend.s3.eu-central-1.amazonaws.com/index.html` (output `frontend_https_url`) serves the same files over HTTPS, so the API's CORS allows both origins. They are different origins to a browser, so the access code in localStorage is per address. Limits of the REST endpoint: no index document (the URL must end in `/index.html`) and no custom domain; CloudFront + ACM is the upgrade if either matters.
- **Poller credentials: keep the IAM user.** Long-lived key, scoped to `s3:PutObject` plus CloudWatch metrics/logs. IAM Roles Anywhere (self-signed CA, free) was evaluated and judged not worth the setup and cert-rotation burden for one device. Good interview talking point.
- **Per-camera threads, not a sequential loop.** The old sequential loop let busy wired cameras delay C660's poll, growing its backlog and its awake time (battery drain).
- **Night mode slows polling, it does not stop it.** A hard stop causes one huge catch-up session at dawn.
- **Network fix for changing IPs: DHCP reservation on the router, not MAC discovery in code.** MAC-to-IP lookup needs ARP/raw sockets (privilege), fails across VLANs, and adds a per-cycle failure mode. Router is a TP-Link Deco M4R pair; reservations are set in the Deco app (More > Advanced > Address Reservation), not the web page.
- **Heartbeat + error metrics come from the poller itself**, because `ClipsProcessed` alone cannot distinguish "poller broken" from "quiet night".
- **Alarm design:** `ClipsProcessed` metric filter has `default_value = 0` and the alarm uses `treat_missing_data = "breaching"`. An earlier "alarm never fired" incident was actually an unconfirmed SNS email subscription (confirmation mail was in spam).
- **GitHub OIDC role stays broad** (service-level wildcards): pragmatic for a personal project. Broad, but not able to escalate to admin through IAM: see the permissions boundary below.
- **IAM policies: inline for strictly 1:1 permissions, managed when shared.** Lambda permissions are inline `aws_iam_role_policy` because each is scoped to one function's resources and never reused; inline policies share the role's lifecycle, so they can't be orphaned. This follows AWS guidance (managed by default, inline for a strict one-to-one relationship). Managed-policy versioning adds little when git is the version history. `modules/lambda` creates only the role and an inline policy that lets the function write to its own log group (not the AWS-managed `AWSLambdaBasicExecutionRole`, which allows any log group in the account); each caller attaches its own policies to `module.<x>.role_name`, which keeps the module interface small as permission types grow (e.g. Rekognition). Accepted downside: the module doesn't force a Lambda to define its permissions, so a missing one shows up as a runtime `AccessDenied`, not a plan error. The poller user's managed policies predate this rule; leave them unless they're touched for another reason.
- **Dependabot PRs skip the `Terraform plan` job.** Workflows triggered by Dependabot can't read Actions secrets, so the plan job failed at the OIDC login. Its bumps (pip pins, the image's base digest) can't change the plan, so the job is skipped for `dependabot[bot]` instead of adding the plan role to Dependabot's secret store: bot-authored PRs never get AWS credentials. Revisit if Dependabot is ever set up for Terraform providers, where a plan would matter.
- **Footage retention: 60 days** (`clips_ttl_days`; S3 lifecycle for `clips/` and `thumbnails/`, plus the DynamoDB `ttl` the processor writes). Longer than the EDPB's guidance (Guidelines 3/2019: a few days; beyond 72 h needs justification) on purpose: we've needed footage older than 30 days, and a neighbor once asked for footage from more than 30 days back. Deleted versions are kept 7 days (the undo window), so footage lasts at most ~67 days. Clips move to STANDARD_IA at day 30; there's no Glacier transition, because Glacier bills a 90-day minimum. `thumbnails/` had no lifecycle rule before 2026-10-22, so thumbnails never expired.
- **Base image pulls: ECR Public login in deploy, one retry everywhere.** Anonymous ECR Public pulls are rate-limited per source IP, and GitHub-hosted runners share IPs, so builds failed now and then with `429 Too Many Requests` on the base image's manifest (fetched on every build, even when everything is cached). `deploy.yml` logs in to ECR Public (the deploy role has `ecr-public:GetAuthorizationToken` and `sts:GetServiceBearerToken`; the latter can't be conditioned on `sts:AWSServiceName`, because ECR Public checks it internally without that key, which denied the first deploy), so its pulls count against the account's quota. CI's image job has no AWS credentials (Dependabot PRs can't have any), so both workflows retry the build once after 60 s. Rejected: an ECR pull-through cache (puts the account ID in the `FROM` line and breaks builds without credentials: Dependabot, local, forks) and Docker Hub (tighter anonymous limits).
- **Permissions boundary on every workload identity** (PR `iam-permissions-boundary`, 2026-10-28). Found while reviewing #48: the apply role could already make itself admin through the poller user (put or attach a `*:*` policy, which `CreatePolicy`/`AttachUserPolicy` on `tapo-*` allowed, then `CreateAccessKey`), or through a Lambda role (a `tapo-*` policy on a `tapo-*` role, passed to a new function). #48 added a second route (`PutUserPolicy`), not a new kind. Fix: `tapo-workload-boundary` (bootstrap, `workload_boundary.tf`) is the ceiling for the four Lambda roles and the poller user: S3 get/put/list on the clips bucket, DynamoDB data-plane reads/writes on `tapo-*` tables, `ssm:GetParameter` on `/tapo/*`, writes to `tapo-*` and `/aws/lambda/tapo-*` log groups, `PutMetricData` in `Tapo/Camera`. No IAM, STS, deletes or other services. The apply role may only `CreateRole`/`CreateUser`, put or attach policies, or set a boundary when the target has that boundary (`iam:PermissionsBoundary`), and is explicitly denied removing boundaries or editing the boundary policy. The boundary lives in bootstrap, so CI can't raise its own ceiling.
   - Broad on purpose (what the workloads could plausibly need on this project's resources), because per-function least privilege already lives in the main stack; the boundary only has to make escalation impossible. Accepted friction: giving a workload a new AWS service (e.g. Rekognition) needs a boundary statement first, applied locally, before the main stack can use it.
   - `modules/lambda` requires `permissions_boundary`, so a missing one fails at plan. An unbounded `tapo-*` role or a new IAM user would be denied at apply anyway.
   - Still allowed, and capped by the boundary: `CreatePolicyVersion` on `tapo-*` managed policies and `CreateAccessKey` on the poller user. The CI roles stay unbounded (bootstrap-managed, `ProtectCIRoles` deny).
   - Verified with the IAM policy simulator before applying: every action the five identities use today is allowed with the boundary; an admin policy under the boundary is denied IAM, STS, deletes, state-bucket reads and EC2; the apply role is allowed bounded writes and denied unbounded ones, boundary removal and boundary edits. The authorizer's SecureString decrypt via the `aws/ssm` key policy is also allowed under the boundary. Simulator quirk: it denies any log-stream ARN whose group name contains `/` even under `Resource: "*"`, so Lambda log writes were checked with the group's `:*` ARN.
- **CloudWatch cost: free tier where it's free, not at any price.** Free tier: 10 standard-resolution alarm metrics and 10 custom metrics a month; an alarm using metric math is billed for every metric in its expression. On 2026-10-28 the account was at 10/10 alarm metrics and 9/10 custom metrics (AWS's 85% warning near month end was just that usage building up). `c660-battery` adds one alarm (`tapo-battery-low-c660_street`, about $0.10/month) and `BatteryPercent` (10/10); `PollCyclePaused` is billed only for the hours it's sent. Small costs that buy a real signal are fine (an existing $5/month AWS Budget covers them); avoidable ones aren't, which is why the heartbeat stays single-metric. SLO burn-rate alarms (agreed order, step 4) will need several alarms per SLI, so the free tier won't hold there: budget for it then.
- **No auto-PR workflow.** A PR created with the default `GITHUB_TOKEN` does not trigger other workflows, so CI would not run on it; making it work needs a PAT or GitHub App token. Not worth the extra credential for a solo repo. Use `gh pr create --draft --fill` instead.

## Incident log (lessons)

- Mass auth failures on all cameras: the global Tapo password had been changed and `config.yaml` was stale. Repeated retries had also burned the cameras' login lockout counters. Lesson: verify credentials with ONE attempt per camera, then wait.
- `PermissionError: /var/lib/tapo-poller`: fixed with systemd `StateDirectory=tapo-poller`.
- Restart mid-cycle re-uploaded everything: state was only saved at end of cycle. Fixed with per-clip `persist_clip_progress`.
- "Task was destroyed but it is pending" asyncio warning: caused by closing the event loop every cycle while pytapo async generators were still finalizing. Fixed with one long-lived loop per thread (a rare warning may still appear; GC timing).
- C660 intermittent `No route to host`: battery camera dropping Wi-Fi between wakes. Handled by retry next cycle; watch `PollCycleErrors{CameraName=c660_street}` for patterns.
- Pi lost Wi-Fi after power outage: NetworkManager exhausted autoconnect retries before the router was up; fixed with `connection.autoconnect-retries 0` via `nmcli` plus a global NetworkManager conf.d setting.

## C660 battery (side track, started 2026-10-28)

The C660 ran low after cloudy days; goal is to save its battery remotely, without SSH to the Pi.

- pytapo's `getBatteryStatus()` works on the C660 (checked once by hand): `battery_percent`, `power_mode: SOLAR`, `battery_charging` (`NORMAL` seen; other values not yet), `battery_voltage`, `battery_temperature` (6 °C at the time: Li-ion barely charges near 0 °C, so winter may limit solar charging regardless of sky).
- All three steps go in one branch and PR, `c660-battery`.
- Step 1: cameras with `battery_powered: true` read the battery in the session the poller already opens (no extra wake), log it, and emit `BatteryPercent` (best-effort, never a poll error). Alarm `tapo-battery-low-c660_street` below `battery_low_threshold_percent` (25, below the auto-pause threshold, so it fires only when pausing hasn't stopped the drain). Purpose besides alerting: measure whether polling is a meaningful share of the drain (the camera keeps recording while unpolled) before building a pause.
- Step 2, manual override: `.github/workflows/camera-override.yml` (`workflow_dispatch`: camera, `pause`/`poll`/`clear`, hours 1-168) writes `/tapo/poller/override/<camera>` = `{"mode", "until", "set_by"}`. The poller reads it before every cycle (`ssm:GetParameter` on that path only, inline policy `tapo-poller-read-overrides`). `pause` skips the cycle without contacting the camera; `poll` polls even while auto-paused. Both expire by themselves, because a forgotten pause silently loses footage for days. If SSM is unreachable, the last value read is kept (and still expires); after a restart with SSM down, polling is normal. The parameters are runtime state, not Terraform resources.
   - Role `tapo-github-actions-camera-control` (bootstrap) trusts only the `camera-control` GitHub environment's OIDC subject, not `ref:refs/heads/main`: any job on `main` could otherwise assume both it and the apply role, and the narrow role would isolate nothing. The environment is restricted to `main` in the repo settings, and holds the `AWS_CAMERA_CONTROL_ROLE_ARN` secret. The apply role gained `iam:PutUserPolicy`/`DeleteUserPolicy` on the poller user only, for the inline policy.
   - A skipped cycle still emits `PollCycleCompleted` (the heartbeat means "the thread ran", whatever the outcome), so a pause doesn't page but a dead thread still does, plus `PollCyclePaused`, which nothing alarms on. Paused cycles are what the SLO work should subtract from C660's poll-success numbers. Rejected: a metric-math heartbeat (`completed + paused`), because metric math bills every metric in the expression as an alarm metric: +4 over the free tier's 10. See "CloudWatch cost" under Decisions.
- Step 3, auto-pause (per camera, `auto_pause` in `config.yaml`; needs `battery_powered`): below 35% downloads stop, above 55% they resume, and the alarm stays at 25% (decided 2026-10-28; the C660 drains fast, hence the high pause threshold). While paused, the worker still wakes on its normal interval and emits `PollCycleCompleted` + `PollCyclePaused` without contacting the camera; every `probe_interval_seconds` (default 3 h) it opens a session that only reads the battery, and if it's above 55% it downloads in that same session. The decision is kept in `state.json`, so a restart doesn't resume polling at low battery. Invalid settings disable auto-pause for that camera (logged as an error) instead of stopping the poller. Built together with steps 1 and 2 at the user's request, before step 1's data was in: the `BatteryPercent` history still answers whether pausing saves enough to keep it on.
   - Accepted: the first session after a long pause downloads the whole backlog. Fine once recharged; revisit (e.g. newest N clips only) if that session itself drains the battery noticeably.
- Tests: `tests/test_poller.py` covers override parsing and SSM reads (moto), the thresholds, settings validation, and `poll_camera` while auto-paused (pytapo is stubbed). `poller.py` now parses its CLI arguments in `main()`, so tests can import it. `camera_worker`'s loop itself isn't unit-tested.
- Rollout order: apply `bootstrap/` locally, create the `camera-control` environment (deployment branches: `main`) with the `AWS_CAMERA_CONTROL_ROLE_ARN` secret, then merge (deploy applies the main stack), then deploy `poller.py` to the Pi, add `battery_powered`/`auto_pause` to C660's entry in `config.yaml` and restart.
