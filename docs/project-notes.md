# Project notes: decisions, history, backlog

Imported by CLAUDE.md. Update this file when a decision is made or a backlog item changes state.

## Decisions (and why)

- **API auth: shared-secret Lambda authorizer.** `x-api-key` header checked against an SSM SecureString (generated by Terraform `random_password`), constant-time compare, 5-minute authorizer cache. Chosen over Cognito (free at this scale, but needs an OAuth/PKCE frontend rewrite plus CloudFront + ACM for HTTPS, and makes mobile access more awkward) and over a WAF IP allowlist (blocks access from other networks). Swapping to a Cognito JWT authorizer later only touches the API Gateway layer; the query Lambda is unaffected. CORS must allow the `x-api-key` header. Rotate with `terraform apply -replace=random_password.api_shared_secret`.
- **Frontend over HTTPS without CloudFront: use the bucket's regional REST endpoint.** The S3 website endpoint is HTTP only. `https://vladaya-tapo-cameras-frontend.s3.eu-central-1.amazonaws.com/index.html` (output `frontend_https_url`) serves the same files over HTTPS, so the API's CORS allows both origins. They are different origins to a browser, so the access code in localStorage is per address. Limits of the REST endpoint: no index document (the URL must end in `/index.html`) and no custom domain; CloudFront + ACM is the upgrade if either matters.
- **Poller credentials: keep the IAM user.** Long-lived key, scoped to `s3:PutObject` plus CloudWatch metrics/logs. IAM Roles Anywhere (self-signed CA, free) was evaluated and judged not worth the setup and cert-rotation burden for one device. Good interview talking point.
- **Per-camera threads, not a sequential loop.** The old sequential loop let busy wired cameras delay C660's poll, growing its backlog and its awake time (battery drain).
- **Night mode slows polling, it does not stop it.** A hard stop causes one huge catch-up session at dawn.
- **Network fix for changing IPs: DHCP reservation on the router, not MAC discovery in code.** MAC-to-IP lookup needs ARP/raw sockets (privilege), fails across VLANs, and adds a per-cycle failure mode. Router is a TP-Link Deco M4R pair; reservations are set in the Deco app (More > Advanced > Address Reservation), not the web page.
- **Heartbeat + error metrics come from the poller itself**, because `ClipsProcessed` alone cannot distinguish "poller broken" from "quiet night".
- **Alarm design:** `ClipsProcessed` metric filter has `default_value = 0` and the alarm uses `treat_missing_data = "breaching"`. An earlier "alarm never fired" incident was actually an unconfirmed SNS email subscription (confirmation mail was in spam).
- **GitHub OIDC role stays broad** (service-level wildcards): pragmatic for a personal project.
- **IAM policies: inline for strictly 1:1 permissions, managed when shared.** Lambda permissions are inline `aws_iam_role_policy` because each is scoped to one function's resources and never reused; inline policies share the role's lifecycle, so they can't be orphaned. This follows AWS guidance (managed by default, inline for a strict one-to-one relationship). Managed-policy versioning adds little when git is the version history. `modules/lambda` creates only the role and basic execution; each caller attaches its own policies to `module.<x>.role_name`, which keeps the module interface small as permission types grow (e.g. Rekognition). Accepted downside: the module doesn't force a Lambda to define its permissions, so a missing one shows up as a runtime `AccessDenied`, not a plan error. The poller user's managed policies predate this rule; leave them unless they're touched for another reason.
- **Dependabot PRs skip the `Terraform plan` job.** Workflows triggered by Dependabot can't read Actions secrets, so the plan job failed at the OIDC login. Its bumps (pip pins, the image's base digest) can't change the plan, so the job is skipped for `dependabot[bot]` instead of adding the plan role to Dependabot's secret store: bot-authored PRs never get AWS credentials. Revisit if Dependabot is ever set up for Terraform providers, where a plan would matter.
- **No auto-PR workflow.** A PR created with the default `GITHUB_TOKEN` does not trigger other workflows, so CI would not run on it; making it work needs a PAT or GitHub App token. Not worth the extra credential for a solo repo. Use `gh pr create --draft --fill` instead.

## Incident log (lessons)

- Mass auth failures on all cameras: the global Tapo password had been changed and `config.yaml` was stale. Repeated retries had also burned the cameras' login lockout counters. Lesson: verify credentials with ONE attempt per camera, then wait.
- `PermissionError: /var/lib/tapo-poller`: fixed with systemd `StateDirectory=tapo-poller`.
- Restart mid-cycle re-uploaded everything: state was only saved at end of cycle. Fixed with per-clip `persist_clip_progress`.
- "Task was destroyed but it is pending" asyncio warning: caused by closing the event loop every cycle while pytapo async generators were still finalizing. Fixed with one long-lived loop per thread (a rare warning may still appear; GC timing).
- C660 intermittent `No route to host`: battery camera dropping Wi-Fi between wakes. Handled by retry next cycle; watch `PollCycleErrors{CameraName=c660_street}` for patterns.
- Pi lost Wi-Fi after power outage: NetworkManager exhausted autoconnect retries before the router was up; fixed with `connection.autoconnect-retries 0` via `nmcli` plus a global NetworkManager conf.d setting.

## Terraform cleanup (agreed 2026-10-06; all four steps done)

Review done; work in this order, one small PR each, every PR with a `plan` attached. PRs #14 (repo hygiene) and #15 (random provider + fmt) should be merged first.

1. **Small fixes** (done in PR `terraform-small-fixes`; also fixed: local and CI zips had different hashes because of file permissions (664 vs 644), so every local `plan` showed false Lambda redeploys)
   - Log group race: all three Lambdas name their log group from the function, so it is created after the function; an early invocation auto-creates it and the apply fails. Name it from a fixed string and make the function `depends_on` it (or use `logging_config`).
   - `monitoring.tf` hardcodes `/aws/lambda/tapo-clip-processor` and `FunctionName`; reference the resources instead.
   - API CORS `allow_origins = ["*"]`: restrict to the frontend website URL.
   - `alert_email` has no default (breaks the convention) and lives in `monitoring.tf`; move to `variables.tf`.
   - `deploy.yml`: delete the "Release state lock on failure" step (queries the deleted DynamoDB lock table; auto force-unlock is unsafe anyway), add a `concurrency:` group, drop the duplicate `update-function-code` job (Terraform already owns Lambda code via `archive_file`), fix the nonexistent `lambda_function_name_query` output reference.
   - Delete `removed.tf` (already applied).
2. **Regroup files by component (zero-diff)** (done in PR `terraform-regroup`): `clips.tf` (clips bucket + DynamoDB), `processor.tf` (Lambda + IAM + S3 trigger), `api.tf` (query + authorizer Lambdas, API Gateway, their IAM), `frontend.tf`, `poller.tf` (IAM user/policies/key), `monitoring.tf`; all variables in `variables.tf`, all outputs in `outputs.tf` (keep output names: `deploy.yml` uses them). Then update the CLAUDE.md layout section (also add `bootstrap/`). Plan must show no changes.
3. **`modules/lambda`** (done in PR `terraform-lambda-module`): archive + role + basic policy + log group + function. 12 `moved {}` blocks in `moved.tf`; the plan shows 12 moves and 0 changes. Least-privilege policies deliberately stay in the callers. `moved` blocks rather than `terraform state mv`: `deploy.yml` auto-applies on push to `main`, so moving state outside the pipeline would leave a window where an apply plans to destroy and recreate everything; `moved` blocks are reviewed in the PR and applied atomically. `moved.tf` deleted after apply (PR `terraform-post-module-cleanup`).
4. **ffmpeg layer → container image** (done; the function has run the image since 2026-10-12). The old layer (account `175033217214`, `ffmpeg:1`) is from June 2019: an unpatched ffmpeg of unknown provenance and license, which its owner can delete or unshare (breaking the next apply that touches the function). Layer versions are immutable, so the risk is staleness, provenance and availability, not code swapping. Chosen: package the processor as a container image in ECR (also covers the GitHub Actions ECR/OIDC learning goal). Started with Debian's ffmpeg, then switched to a minimal source build (below) after the first scan.
   - ~~ffmpeg from Debian packages~~ (4a, superseded): visible to ECR scanning and patched by Debian, but at ~875 MB it pulled in libtiff, librsvg, libxml2 and similar, which produced every scan finding below.
   - 4a (PR `processor-image-ecr`): ECR repo (immutable tags, scan on push, keep 5 images), Dockerfile + smoke test (handler's `generate_thumbnail` on synthetic H.264/H.265), CI build on PRs, deploy pushes after apply and reports scan findings, Dependabot for base digest and pip pins. CI apply role gets `ecr:*` on `repository/tapo-*` (bootstrap; apply before merging).
   - First scan (2026-10-08): 1 critical, 15 high, all in ffmpeg's transitive libraries or the base (libtiff, librsvg, jpeg-xl, libxml2, cJSON, expat, zlib), none in ffmpeg itself. Debian has no fixed versions yet, so a rebuild doesn't clear them. The processor only decodes our own H.264/H.265 clips to JPEG, so these code paths aren't reached. That makes them low real risk, but they're permanent scanner noise. That led to the minimal build below.
   - **Minimal source-built ffmpeg** (PR `processor-minimal-ffmpeg`): FFmpeg 9.0.2 from the GPG-verified tarball (release key `FCF9 86EA 15E6 E293 A564 4F10 B432 2F04 D676 58D8`), pinned by SHA-256 via `ADD --checksum`. `--disable-everything` plus: file protocol, mov demuxer, h264/hevc parsers and decoders, mjpeg encoder, image2 muxer, scale filter. Static, LGPL-only (no `--enable-gpl`), 7.5 MB, links only libc/libm; the image is 258 MB. Smoke test uses committed synthetic fixtures (`testdata/`, H.264+AAC and HEVC+AAC) because this ffmpeg can't encode. CI caches the compile stage (GitHub Actions cache).
   - **Accepted tradeoff:** ECR scanning only sees OS packages, so it can't see this ffmpeg, and Dependabot can't bump it. Track it by hand: watch FFmpeg security releases (https://ffmpeg.org/security.html), and to bump, verify the new tarball's signature and update `FFMPEG_VERSION` and `FFMPEG_SHA256`. Its exposure is small (two decoders plus one demuxer, and only our own clips as input), but H.264/HEVC decoders are frequent CVE sources, so don't let it go stale. Option: a scheduled workflow that opens an issue when a newer 9.0.x appears.
   - Real-clip check (2026-10-09, clips deleted afterwards), run with Lambda-like limits (512 MB, 0.3 vCPU):
     - Cameras produce C225 H.264 High 2560x1440; C325 H.264 Main 2688x1520, full-range `yuvj420p`; C660 **HEVC `hev1` 3840x2160**. All have mono AAC audio.
     - Minimal image: thumbnails 1.2 s / 1.5 s / 4.5 s, all on the first attempt (no fallback), and full decodes of every clip succeed.
     - The `SEI type 764 truncated` messages on the H.264 cameras are vendor SEI that ffmpeg doesn't recognize. They're identical with Debian's ffmpeg and harmless.
     - Debian's ffmpeg was OOM-killed fully decoding the 4K HEVC clip at 512 MB; the minimal build was not.
   - Thumbnails capped at 1280 px wide (PR #23; `THUMBNAIL_MAX_WIDTH`, never upscales). Verified on both the minimal image and the old layer. Existing full-size thumbnails just expire.
   - Scan after the minimal build (2026-10-09): **1 HIGH (zlib, base image)**, down from 1 critical, 15 high, 7 medium and 1 low. Dependabot picks up the fix once Debian ships it.
   - 4b prep (PR `processor-image-prep`, no behavior change): `modules/lambda` supports `image_uri` (digest-pinned, validated) besides `source_file`; ECR repository policy lets only `tapo-clip-processor` pull; `scripts/backfill_processor.py`.
   - 4b switch (PR `processor-image-switch`, applied 2026-10-12; the backfill dry run afterwards found no dropped clips): processor uses the image by digest; `deploy.yml` builds/pushes the image before `terraform apply`. Runbook in the PR. The S3 invoke permission's `statement_id` was renamed so it gets recreated: replacing the function deletes its resource policy, but the permission's inputs are unchanged, so Terraform would otherwise leave S3 unable to invoke, silently.
   - No weekly scheduled rebuild (dropped from the plan): with the minimal build every input is pinned (base digest, ffmpeg tarball hash, pip versions), so a rebuild produces the same image. Updates arrive as Dependabot PRs or a manual `FFMPEG_VERSION` bump, then deploy.
     - Zip→image forces function replacement, and S3 events during the gap are lost. Apply while nothing uploads (pause `tapo-poller`, or during a camera/internet outage), then run `scripts/backfill_processor.py --since <date> [--invoke]`. It re-invokes the processor for clips whose row is missing or not `complete`; it's a dry run by default.
     - Doesn't need live cameras to verify: `scripts/backfill_processor.py --key <existing clip> --invoke` sends a synthetic S3 `ObjectCreated` event; it just regenerates that clip's thumbnail and metadata.
     - The lifecycle keeps 5 images; make sure the function's digest is always one of them (it is, as long as each deploy updates the function).
   - 4c (PR `processor-layer-cleanup`): removed the `LambdaLayers` statement (`lambda:GetLayerVersion` on any account's layers) from the CI apply role, and the now-unused `layers` input from `modules/lambda`. The role change is in `bootstrap/`, so it is applied locally, not by CI.

Not doing: splitting the main stack into multiple states. `bootstrap/` already provides the privilege-boundary split; more stacks would be overkill at ~100 resources.
Known and accepted: `aws_iam_access_key` and `random_password` put secrets in tfstate. This is acceptable because the state bucket is encrypted and access-restricted.
